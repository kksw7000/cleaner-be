# 알림 기능 학습 가이드

## 1. 역할과 사용자 흐름

알림 기능은 예약 접수·상태 변경·예약 삭제 이벤트를 로그인한 회원의 알림으로 저장합니다. 프론트엔드는 홈 미리보기 API에서 최신 3개와 전체 미읽음 개수를 가져오고, 알림 보관 페이지 API에서 전체 항목을 페이지 단위로 확인합니다. 알림을 열면 읽음 시각이 저장되며, 오래된 알림은 자동 삭제하지 않습니다.

## 2. 데이터와 삭제 관계

`V7__create_member_notifications.sql`은 알림의 유형, 표시 문구, 생성 시각, 읽음 시각, 회원 ID, 예약 ID를 저장합니다. 회원 삭제 시 회원의 알림도 함께 삭제되도록 회원 외래 키에 `ON DELETE CASCADE`를 둡니다. 예약 삭제 시 알림은 남기되 예약 연결만 `ON DELETE SET NULL`로 비워 “예약이 삭제되었습니다” 문구를 계속 보여줍니다.

읽지 않은 항목은 `readAt`이 `null`이고, 읽으면 읽은 시각이 기록됩니다. 화면은 이 값을 이용해 미읽음과 읽음을 다르게 표시합니다.

## 3. API

- `GET /api/notifications/home`: 최신 3개와 전체 미읽음 수를 반환합니다.
- `GET /api/notifications?page=0&size=10`: 최신순 알림 페이지를 반환합니다. 페이지 크기는 1~100입니다.
- `GET /api/notifications/unread-count`: 전체 미읽음 수를 반환합니다.
- `GET /api/notifications/stream`: JWT로 인증된 연결에 커밋된 신규 알림을 SSE `notification` 이벤트로 실시간 전달합니다.
- `PATCH /api/notifications/{id}/read`: 로그인 회원 본인의 알림 하나를 읽음 처리합니다.
- `PATCH /api/notifications/read-all`: 로그인 회원의 미읽음 항목을 모두 읽음 처리하고 처리 개수를 반환합니다.

회원 ID는 요청 파라미터가 아니라 JWT 인증 정보에서 가져옵니다. 알림 ID 조회에도 회원 ID를 함께 조건으로 사용해 다른 회원의 알림을 읽거나 수정하지 못하게 합니다.

## 4. 예약 이벤트

예약 생성 시 `RESERVATION_RECEIVED` 알림을 저장합니다. 관리자의 예약 상태 변경은 실제 상태가 달라진 경우에만 새 알림을 만들며, 승인·거절·취소·완료 상태별로 유형과 문구를 구분합니다. 예약 상태 변경과 알림 저장은 같은 트랜잭션에 참여해 한쪽만 반영되는 일을 방지합니다.

관리자 예약 삭제는 삭제 알림을 먼저 저장하고 예약을 제거합니다. DB 외래 키가 알림의 예약 참조만 비우므로 알림 문구는 보관됩니다.

## 5. 실시간 알림과 페이지 표시

홈 미리보기는 항상 최신 3개이며 알림 보관 화면은 페이지 단위입니다. 미읽음 배지 개수는 홈에 보이는 항목 수와 무관하게 회원의 전체 미읽음 개수입니다.

SSE 연결은 브라우저가 페이지를 보고 있는 동안 단방향으로 신규 알림을 전달합니다. 알림 데이터는 먼저 DB에 저장하고 트랜잭션 커밋 후에만 `notification` 이벤트를 발행하므로 실패로 롤백된 예약 알림이 화면에 먼저 뜨지 않습니다. 연결은 회원 ID별로 나뉘고 완료·오류·30분 시간 초과 때 서버에서 정리합니다. 클라이언트는 연결이 끊기면 다시 연결하고 홈/알림 API로 최신 상태를 동기화해야 합니다. 프로세스 메모리에 연결을 보관하므로 여러 백엔드 인스턴스 간 fan-out은 메시지 브로커가 추가되기 전까지 제공하지 않습니다.

현재 Access Token은 `Authorization` 헤더로 전달됩니다. 브라우저 기본 `EventSource`는 임의 Authorization 헤더를 지정할 수 없으므로 프론트엔드는 인증 헤더를 넣을 수 있는 `fetch` 스트리밍 클라이언트를 사용하거나, Access Token을 보안 쿠키로 전달하도록 별도의 인증 설계를 해야 합니다. 토큰을 URL 쿼리 파라미터에 넣지 않습니다. 연결 직후 홈/알림 API를 조회해 스트림이 연결되지 않았던 동안의 알림도 동기화합니다.
